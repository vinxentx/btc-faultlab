## Project Overview

Bitcoin FaultLab is an experimental framework for analyzing Bitcoin network resilience under controlled fault conditions. It runs 128-node Bitcoin regtest networks in Docker, injects crash and network faults, and measures recovery performance.

## Common Commands

```bash
# Run a single experiment with config overrides
python3 run_experiments.py --experiment baseline --runs 1

# Run tier-based experiments (from tier_experiments.json)
python3 run_tier_experiments.py --experiment tier_b_002 --runs 3

# Ansible playbooks (executed automatically by run_experiments.py)
ansible-playbook playbooks/02_deploy.yml           # Start Docker stack
ansible-playbook playbooks/02_prepare_wallets.yml  # Fund wallets
ansible-playbook playbooks/03_run_experiment.yml   # Execute experiment
ansible-playbook playbooks/04_collect.yml          # Collect results

# Analyze results
python3 analysis/metrics.py results/<run_id>/
python3 analysis/aggregate_replications.py results/<experiment>-*/
```

## Architecture

### Execution Flow
```
run_experiments.py → Ansible Playbooks → Docker Compose (128 nodes)
                                              ↓
                   ┌──────────────────────────┴──────────────────────────┐
                   │                                                      │
            block_scheduler.py                                    txgen.py (8 shards)
            (deterministic mining)                               (transaction injection)
                   │                                                      │
                   └──────────────────────────┬──────────────────────────┘
                                              ↓
                                      analysis/metrics.py
```

### Key Components

| Component | File | Purpose |
|-----------|------|---------|
| Experiment Runner | `run_experiments.py` | Orchestrates single experiment runs |
| TX Generator | `files/txgen.py` | Two-phase TX injection (prepare → inject) |
| Block Scheduler | `files/block_scheduler.py` | Deterministic block mining at fixed intervals |
| Wallet Funding | `files/funding_setup.py` | Initial UTXO distribution to shard wallets |
| Metrics | `analysis/metrics.py` | Calculates latency, throughput, availability |

### Two-Phase Transaction Architecture
1. **Phase 1 (Preparation)**: Pre-sign transactions using wallet RPC before observation
2. **Phase 2 (Injection)**: Broadcast via `sendrawtransaction` - fast, no wallet lock

### Configuration Hierarchy
1. `group_vars/all.yml` - Base parameters (node count, tx rate, crash settings)
2. `tier_experiments.json` - 47 predefined experiment configs
3. `temp_override.yml` - Runtime overrides (generated by run_experiments.py)

### Key Parameters
```yaml
node_count: 128              # Bitcoin nodes
tx_rate: 20                  # Total tx/s (split across 8 shards)
crash_fraction: 0.25         # 25% of nodes crash
crash_duration_s: 120        # Downtime before recovery
crash_mode: burst|staggered  # Simultaneous vs sequential crashes
stagger_period_s: 90         # Time window for staggered crashes
warmup_s: 120                # Stabilization before measurement
observe_s: 480               # Observation window
cooldown_s: 60               # Confirmation buffer after observation
```

### Crash & Recovery Logic

Located in `roles/experiment/tasks/main.yml`. Two crash modes with individual per-node tracking:

**Burst Mode** (`crash_mode: burst`):
- All selected nodes crash simultaneously
- All recover simultaneously after `crash_duration_s`

**Staggered Mode** (`crash_mode: staggered`):
- Nodes crash sequentially over `stagger_period_s` window
- Each node has **individual downtime tracking**: waits exactly `crash_duration_s` from its own crash time
- Recovery is staggered matching crash order

```
Timeline (staggered, 3 nodes, stagger_period=90s, crash_duration=120s):

Node1: crash@0s  ───────────────────────────────── recover@120s
Node2:      crash@30s  ───────────────────────────────── recover@150s
Node3:           crash@60s  ───────────────────────────────── recover@180s
       |_________|                                  |_______________|
       stagger_period                               staggered recovery
```

**Event Log Structure**:
```
crash_start mode=staggered duration=120s    # Injection begins
node_crash node=node05 index=0              # Individual crash events
node_crash node=node12 index=1
crash_complete                              # Last node stopped
recovery_node_start node=node05 index=0     # Individual recovery events
recovery_start nodes=node05,node12,...      # First node restarted
recovery_node_start node=node12 index=1
recovery_complete nodes=...                 # All nodes synced (height >= network)
```

**Recovery Modes**:
- `full_resync`: Restart with `-reindex` flag (complete blockchain re-validation)
- `fast_resync`: Normal restart (incremental sync from peers)

### Results Structure
```
results/<run_id>/
├── metadata.yml          # Exact parameters used
├── events.log            # Timeline: crash_start, recovery_complete, etc.
├── txlog.csv             # All submitted transactions
├── mining.csv            # Block events from block_scheduler
├── confirmations.csv     # TX confirmations with block hashes
├── metrics.json          # Computed performance metrics
└── nodeXX.log            # Bitcoin Core debug logs
```

## Important Patterns

### RPC Client (txgen.py)
Uses persistent HTTP connections with thread-local storage. Auth is `base64(user:pass)`.

### Event Logging
All events use ISO8601 UTC timestamps:
```
2025-01-05T10:30:00Z crash_start mode=burst nodes=node01,node02
```

### Metrics Measurement
- **Availability**: `confirmed_txs / submitted_txs` (with 60s confirmation buffer)
- **Latency**: Time from TX submission to 6-confirmation
- **Recovery Time**: `recovery_complete - crash_start` from events.log

### Shard Wallets
8 parallel wallets (`wallet_shard_a` through `wallet_shard_h`) each with isolated UTXO pools. Pool size must be ≥ `(warmup_s + observe_s) × rate_per_shard × 1.5`.
